# Git 審核與分批提交

審核以 Git 的提交／分支、檔案差異與工作區狀態描述版本。報告記錄基準 ref、檔案範圍、測試命令／結果、Standards／Spec 結論及限制。

## 審核流程

1. 讀取 `git status --short`，確認 staged、unstaged 與 untracked 範圍。先核對來源對話與票據，確定負責者及唯一寫入範圍。
2. 以最近一次已審核提交或明確分支作為基準。已提交變更用 `git diff <base>...HEAD -- <paths>`；待提交變更另外讀取 `git diff --cached -- <paths>`、`git diff -- <paths>` 及 untracked 檔案全文。
3. 對指定範圍做兩軸審核與必要驗證。主審是唯一 runner，實作者只編寫案例。依票據規定保留限定 PASS 與集中整合驗收的界線。
4. 完成前再次檢查相同 Git 差異與狀態。來源在審核期間改動時，先補審受影響內容與重驗，再更新放行；舊結果只適用於已驗證的內容與範圍。

## 分批提交

- 按功能與相依關係提交，將必要契約、實作及對應案例放在同一批。共用檔先提交其共同基礎，再處理消費端。
- 每批先檢查 staged diff、檔案清單與 `git diff --cached --check`，再 commit。完成後確認預期內容已提交、工作區剩餘內容屬於下一批。
- 本機快取與 scratch 產物依 ignore 規則保存。其他已授權的修改均須納入清單，避免遺漏；來源對話仍在寫入時，協調完成後才提交該範圍。
- Commit 保存的是工作基線。通過與 HOLD 仍以票據、審核關卡及實際驗證為準；整理提交不會把未完成的功能或已知失敗升格為通過。

歷史報告保留當時的測試結果、問題與範圍；後續審核直接從 Git 的基準與差異取得版本資訊。
