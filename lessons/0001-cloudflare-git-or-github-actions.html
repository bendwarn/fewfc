誰負責按下 Deploy？

這一課只學一件事：分辨 Cloudflare Git integration 與 GitHub Actions，並為 fewfc 選出唯一的部署負責者。

先講結論：Cloudflare Git integration 啟用後會自動部署，不需要 Action YAML；但 fewfc 應保留現有 GitHub Actions，並避免再啟用 Cloudflare 的 production 自動部署。

兩條路線是平行的

路線 A：Cloudflare Builds

在 Dashboard 授權 GitHub App 並連接 repository。push 發生後，由 Cloudflare checkout、build、deploy。

設定放在 Cloudflare Dashboard，不會建立或讀取 GitHub workflow 來決定部署流程。

路線 B：GitHub Actions

GitHub 讀取 .github/workflows/ci-cd.yml，先跑測試，再呼叫 Wrangler Action。

Cloudflare 只是接受 API token 驗證過的 deploy，不負責控制前面的 gates。

A. push → Cloudflare GitHub App → Build → Deploy B. push → GitHub Actions → Tests → Migration → Wrangler Deploy

「自動」從何時開始？

不是把 wrangler.toml push 上去就會自動整合。你必須先在 Cloudflare Dashboard 對某個 Worker 連接 repository、授權 GitHub App，並指定 production branch。完成一次設定後，後續 push 才會自動觸發。

為何 fewfc 選 GitHub Actions

  • Rust tests、Web unit tests、typecheck 與 Playwright E2E 都必須先成功。
  • D1 migrations 必須在 Worker deploy 前執行。
  • staging 會在 main 通過檢查後自動部署。
  • production 目前設計為手動 dispatch，還能搭配 GitHub Environment approval。

Cloudflare Builds 可以自訂 build/deploy commands，但把上述跨語言測試與核准流程全部搬過去，會比保留現有 workflow 更複雜。

快速檢查

情境：你保留 GitHub Actions 的 deploy job，又在 Cloudflare 連接同一 repository，兩邊都監聽 main。一次 push 後誰會 deploy？

  1. 路線一會單獨部署
  2. 路線二會單獨部署
  3. 兩路都會各自部署
查看答案

答案是 3：兩邊各自執行部署。它們是獨立的觸發器，不會自動互相等待或去重。

主要來源

先讀 Cloudflare 官方的 Git integration；再比較官方的 GitHub Actions 路線。
